# 0010. OpenSandbox Containerized Execution & Filesystem Sandboxing

Date: 2026-10-31
Status: Accepted

## Context

In [0008. Gitea-Backed Git Persistence](./0008-git-persistence.md), agent file access was temporarily scoped to `<session_workspace>/data/` using `FilesystemBackend(virtual_mode=True)`. While this restricted file tools from reading `agent/config/`, `agent/state/`, or `.git/`, it did not provide an isolated execution container for shell commands (`execute`) or protect the host/backend container from untrusted agent execution.

Seamus requires full container sandboxing using [`langchain-sandbox-opensandbox`](https://github.com/AyushSonuu/langchain-sandbox-opensandbox) (`OpenSandboxBackend`) backed by a locally hosted `opensandbox-server` running in its own container, mounting only the session's Git-tracked `data/` directory into the sandbox container as the agent's operational directory.

## Decision

1. **OpenSandbox Backend Integration (`seamus.harness.sandbox`)**:
   - Add `langchain-sandbox-opensandbox` (`langchain_opensandbox`) and `opensandbox` as runtime dependencies.
   - Implement `SeamusOpenSandboxBackend` (subclassing `OpenSandboxBackend`) in `src/seamus/harness/sandbox.py` and replace `FilesystemBackend` in `SessionAgentRunner._build_deep_agent()`.
   - `SeamusOpenSandboxBackend` lazily provisions a session-scoped `SandboxSync` container on first sandbox operation (`id`, `execute`, `upload_files`, `download_files`), allowing runners to be instantiated for historical SSE replay or offline tests without eagerly starting a container.
   - Route sandbox `execd` command and file operations through the `opensandbox-server` proxy (`use_server_proxy=True`) so the backend service only communicates with `opensandbox:8080`.

2. **Runtime-Autogenerated Sandbox API Key**:
   - The OpenSandbox server API key must never be exposed to users, `.env.template`, or external APIs.
   - On startup, the runtime autogenerates a 256-bit cryptographic token (`secrets.token_urlsafe(32)`) stored in an internal runtime key file (`/var/run/seamus-opensandbox/api_key` shared via the internal `opensandbox-auth` Docker volume in Compose, or `.seamus/opensandbox/api_key` with `0600` permissions in local runs).
   - The `opensandbox` container entrypoint loads or generates this key and exports `OPENSANDBOX_SERVER_API_KEY` before launching `opensandbox-server`, ensuring the lifecycle API always operates with authentication enabled.

3. **Git-Tracked Operational Directory Mount (`/workspace`)**:
   - Mount only `<session_workspace>/data/` into the sandbox container at `/workspace` (configurable via `OPENSANDBOX_WORKDIR`).
   - In Docker Compose (`OPENSANDBOX_WORKSPACE_VOLUME=seamus-workspaces`), mount via `Volume(name="workspace", mount_path="/workspace", pvc=PVC(claim_name="seamus-workspaces"), sub_path=f"{agent_id}/{session_id}/data")`.
   - In local host mode (`OPENSANDBOX_WORKSPACE_VOLUME` unset), mount via `Volume(name="workspace", mount_path="/workspace", host=Host(path=str(data_dir.resolve())))`.
   - Repository internals (`.git/`), configuration (`agent/config/`), and thread/checkpoint state (`agent/state/`) remain outside the sandbox mount and completely inaccessible to the agent.
   - Because `/workspace` is backed directly by the session's `data/` directory on `seamus-workspaces`, all files created or modified inside `/workspace` by agent file tools or shell commands are automatically staged, committed (`checkpoint:`), and pushed to Gitea by `GitCheckpointSaver`.

4. **System Prompt Operational Directory Guidance**:
   - Provide `build_sandbox_system_prompt(operational_dir="/workspace")` to `create_deep_agent(system_prompt=...)`.
   - Explicitly instruct the agent that its Git-tracked operational directory is `/workspace`, that all persistent project files and deliverables must be read from and written under `/workspace`, and that anything outside `/workspace` in the sandbox container filesystem is transient and discarded when the sandbox terminates.

5. **Containerized Local OpenSandbox Server (`opensandbox/`, `docker-compose.yml`, `run.sh`)**:
   - Package `opensandbox-server` in its own container (`opensandbox/Dockerfile`, `opensandbox/sandbox.toml`, `opensandbox/entrypoint.sh`) orchestrated by `docker-compose.yml`.
   - Mount `/var/run/docker.sock:/var/run/docker.sock` so `opensandbox-server` provisions sibling sandbox containers on the host Docker daemon, with `extra_hosts: ["host.docker.internal:host-gateway"]` and `[proxy] resolve_internal = false`.
   - Update `run.sh` to include `opensandbox` in `--restart` rebuilds and clean up `.seamus/opensandbox` during `--clean`.

6. **Backlog Additions**:
   - Record a **Very High Priority** `TODO` entry in `knowledge/backlog.md` to comprehensively design and enhance the agent system prompt.
   - Record a `TODO` entry in `knowledge/backlog.md` to conduct a thorough security review of the containerized `opensandbox-server` configuration (`/var/run/docker.sock` exposure, `allowed_host_paths`, network/egress policies, and container runtime hardening).

## Consequences

- Agent file operations (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`) and shell commands (`execute`) run inside an isolated OpenSandbox container rather than in the backend service process.
- Persistent agent work in `/workspace` continues to be automatically versioned and pushed to Gitea on every checkpoint while keeping `agent/config/`, `agent/state/`, and `.git/` isolated outside the container.
- Sandbox authentication is handled transparently by the runtime without user configuration burden.
